# V3 工程与创作品质验收

## 工程验收
- 所有 Markdown 内部链接能够指向仓库中存在的文件。
- 原版 `init_chapter_summaries` 与 `validate_project` 回归测试不退化。
- 新版 `v3_gate` 集成测试：未审第4章阻断、独立编辑报告绑定哈希与版本、重大未解决问题阻断、用户批准证据独立登记、改稿和审稿文件变动后重新阻断。
- 快照创建／哈希核验／空目录恢复／恶意 ZIP 路径拒绝。
- 中文正文重复段落检测能识别原文复制；故事账本审计能提示未跟踪变化和相同机制字段，不能替代剧情语义审稿。
- 逐章交接测试使用独立项目：真实试写账本须在每章后通过 `audit_story_state.mjs --upto N --handoff`，缺章、缺字段或账本字段不合契约须失败；在下一章写前查看上章交接的实际记录。工程验收与文学评分分开。
- 本轮只验证本地 ZIP 快照和恢复；Google Drive 不接入、不上传、不作为验收阻断项。未来如启用，另行验证独立任务恢复、上传回读和无人值守写入权限。

## 写作验收：先测开篇，再测长篇
- 固定同一 Gemini 模型、创作简报、起始素材和目标字数，在新会话分别试写：不加载 Skill、只加载原版、只加载 V3。记录实际加载、初稿、修订稿及修订轮次；隐藏版本给独立评审。若宿主自动加载其他 Skill 且无法隔离，不把这组结果记为裸跑。
- 另在同一批固定稿件上比较三组的精评：证据是否对应原文、是否找到关键缺陷、误报、修改建议可操作性。多样本重复改善才归为 Skill 增益；单篇异常或无法排除宿主差异，记为待归因，不推断模型能力上限。
- 盲审稿不得暴露版本身份；至少比较创意不可替代性、人物生命力、开篇吸引力、因果、语言自然度和追读意愿。
- 重点采集“愿不愿意读第4章”和理由，而非只看模型自评分。
- V3 连续创作至少 10 章，记录人物状态断裂、规则矛盾、复用桥段以及返工情况，比较审稿前后版本。
- 对悬疑、仙侠和现实/历史至少覆盖两种不同类型，避免仅优化单一修仙智斗模板。

## 仍然不能声称
- “通过脚本测试” ≠ “精品网文”。
- “独立子 Agent” ≠ “独立人类读者评审”。
- “本地文件在两个 Tasks 中可见” ≠ “永久保存”。
- “已生成 ZIP” ≠ “已成功上传 Drive 并回读验证”。
